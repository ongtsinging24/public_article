# 重構工單的模型派工 —— 為什麼決定模型的是「錯誤可偵測性」而不是「難度」

> **性質：evergreen 方法論**（派工三軸與口徑紀律不涉當時程式碼水位；§3 的 romasys 盤點數字標為
> 時效性快照，2026-09-10 測，只作機制示範，可用附錄腳本重測）。
>
> **觸發**：2026-09-10 要開工 `FEAT_ADD/10-09-2026_romasys技術債盤點與重構順序.md`（九項技術債
> roadmap 卡），user 問「你建議用什麼模型」。往下挖出的其實是三件事：
> **模型該按什麼軸派**、**依賴順序 ≠ 風險順序**、以及**盤點表混口徑會讓驗收對不上帳**。

## 1. 理論框架 —— 派工不是一軸，是三軸

直覺派法是「難的用強模型、簡單的用便宜模型」。這條**單軸直覺會在重構任務上系統性派錯**，
因為它把「認知難度」當成了風險代理變數。真正該看的是三軸：

| 軸 | 問題 | 高分代表 |
|---|---|---|
| **J 判斷密度** | 每個決策點需要多少領域／架構脈絡才能決定？ | 沒有機械規則可套 |
| **D 錯誤可偵測性** | 改錯了，**多久之內、由誰**會發現？ | 高＝立刻紅；低＝半年後靜默出錯 |
| **C 上下文跨度** | 要同時把多少 LOC 放在眼前才動得了刀？ | 高＝跨檔耦合 |

### 1.1 核心洞見：D 軸（可偵測性）比 J 軸（難度）更該決定模型

考慮兩個子項的對照：

| | ③ replay 腳本搬家 | ② `except: pass` 補 log |
|---|---|---|
| 單點認知難度 | 中（`walk_forward` 在 5 檔各自定義，語意要先對齊才能抽） | **極低**（一行 `pass` 改成一行 `log.warning`） |
| 錯了會怎樣 | `tests/run_all.py` 立刻紅 | **什麼都不會發生** |
| 驗收 | `grep`＝0、測試綠 | **沒有任何自動化能驗收「這個 fallback 判對了」** |
| D 軸 | 高 | **極低** |
| 該派 | 便宜模型 | **最強模型** |

②「簡單」是假的簡單。難的不是寫那行 log，是判斷**這個 except 吞掉之後，下游會不會照樣產出
signal**。判錯的成本不是紅燈，是半年後某個 SYM 在資料缺失時默默出了一個看起來正常的訊號。

這與 [[feedback_tool_silence_is_not_clean]]（「工具沒報」≠「這維度乾淨」）是同一個病：
**缺乏告警不等於正確**。②整項就是在把 610 處「沉默」轉成「會說話」。
memory 裡 [[reference_yfinance_oi_zero_is_feed_failure]]（OI=0 當平倉）與
[[reference_sg_levels_as_of_trade_date_not_filename]]（data_table 靜默凍結）兩條，都是這族債
已經真的咬過人的實例。

> **可推廣的派工規則**
> **高 J ＋ 低 D → 最強模型**（錯誤不可回收）
> **中 J ＋ 高 D → 便宜模型**（護欄會接住，讓它試錯）
> **高 C → 長上下文模型**（跨度不足＝盲改，跟模型強弱無關）
>
> 三軸裡 **D 軸最反直覺，也最常被忽略** —— 因為它問的不是「這件事多難」，
> 而是「我做錯了會不會知道」。

### 1.2 C 軸獨立於 J 軸：上下文不足是硬失敗不是軟失敗

④ 拆 `detect_equity_signals`（592 行）時，`equity_signals.py` 1,019 行 ＋
`tests/test_signals.py` 2,997 行必須同窗，否則改了信號語意而測試對應不上，模型會「合理地」
改測試去遷就實作 —— 這是最壞的一種錯，因為它同時破壞了實作與護欄。

C 軸不足**不能用更強的模型補**，只能用更大的窗或更小的切片補。這是與 J 軸正交的資源。

### 1.3 「機械掃描」的非均勻性 —— ① 的反例

① packaging 看起來是純機械（sed 掉 265 處 `sys.path.insert` 樣板）。但實測發現：

```
roma_cli 單檔 12 處 sys.path.insert，**12 處全部落在 897 行的 main() 內部**
（main 自 roma_cli:63 起算至 :960）：
  11 處為 argparse subcommand 分支各自 insert 一次
     → roma_cli:232/279/325/383/425/492/533/588/681/748/798
   1 處在 restart 流程內讀版本字串前 → roma_cli:105
```

**這 12 處不是樣板，是 ④ 巨型函式的症狀。** 機械 sed 過去會留下 12 個空殼（其中 11 個是空殼 subcommand 分支），
而且會讓 ④ 之後的 registry 重構看不到原本的結構痕跡。

> **推論：「機械」是檔案層級的屬性，不是任務層級的屬性。**
> 一個 265 處的掃描裡，可能有 253 處真的機械、12 處是別的債的投影。
> 派工前要先問「這批目標的分布是否均勻」，不均勻就得先切出例外清單交給強模型。

## 2. 依賴順序 ≠ 風險順序

原卡的建議順序按**前置依賴圖**排：① → ③ → ② → ④ → ⑤ → ⑥⑦。
依賴圖回答的是「什麼**做得動**」，不回答「什麼**該先做**」。

九項裡只有 ② 直接影響**交易決策正確性**，其餘八項都是可維護性。而 ② 的前置是「無」。
把唯一影響正確性的項目排在第三順位，是把工程便利性放在系統正確性之前。

**①②可並行的具體理由**：① 動的是檔頭 import 樣板區、② 動的是函式體內 except 區塊 ——
**檔案重疊但區塊不重疊**，merge 衝突面極小。走 [[reference_parallel_session_worktree_runbook]]
各自開 worktree，或至少走 [[feedback_parallel_session_coordination]] 的共享頻道逐檔 staging。

⚠️ ① 的真正風險不在 sed 而在 daemon：改成 editable install 後若 systemd 環境沒裝好，
症狀是「看起來正常但跑舊碼」——見 [[reference_roma_daemon_stale_module_trap]]。
這是低 D 軸失敗（不會紅、會靜默給舊結果），所以 ① 的**驗證環節**要派強模型，
即使**執行環節**是機械的。同一子項的不同階段可以派不同模型。

## 3. 測量：口徑不一致會讓驗收對不上帳

### 3.1 實驗設計

用 AST 解析（非 grep 計數）重測原卡的盤點基線，刻意跑兩個掃描範圍以量化口徑影響：

- **範圍 A**：`romasys/src` only
- **範圍 B**：`romasys/src` ＋ `romasys/tests` ＋ 根層 `roma_cli`（無 `.py` 副檔名，rglob 抓不到）

腳本見 §6 附錄。函式行數＝`end_lineno - lineno`（AST），非 grep `^def` 區間。

### 3.2 結果表（2026-09-10 測，時效性）

| 指標 | A: src only | B: src+tests+cli | 原卡登記值 | 原卡實際口徑 |
|---|---|---|---|---|
| .py 檔數 | 245 | 412 | 414 | `find . -name '*.py'`（含 src/tests 外） |
| 總 LOC | 76,465 | 129,260 | ~129k | **B** |
| 函式總數 | 2,105 | 5,837 | 2,129 | **A** |
| >100 行函式 | 92 | **93** | 93 | **B** |
| >200 行函式 | 21 | **22** | 22 | **B** |
| >400 行函式 | 1 | **2** | 2 | **B** |
| `sys.path.insert` | 87 | 265 | 254 | src+tests（253），**不含 cli** |
| `except Exception` | 610 | 765 | 610 | **A** |
| `except:` 下一行 `pass` | 87 | 94 | ~90 | 模糊 |
| 函式內 import（縮排近似） | 681 | 1,812 | 678 | **A** |

### 3.3 發現：同一張盤點表混了三種口徑

原卡的 `except Exception 610`、`函式內 import 678` 是 **A（src only）**，
但 `>200 行函式 22`、`>400 行 2`、`LOC 129k` 是 **B（含 tests 與 roma_cli）**，
`sys.path.insert 254` 又是第三種（src+tests 不含 cli）。

這不是抄錯，是**每個數字用當下最順手的指令現查**、沒有統一掃描器的必然結果。
後果具體且會咬人 —— 原卡驗收條款寫：

> ④ >200 行函式 22 → ≤ 8

若驗收時用 A 口徑重測，起點其實是 21；而 897 行的 `roma_cli:63 main()` ——
**④ 章節裡列在第一行、佔全項最大工作量的那個函式** —— 在 A 口徑下根本不在分母裡。
拆完它，A 口徑的數字不會動。

> **這與 rr3/rr4 欄位換口徑那條是同一個原則的另一面**（見
> [[reference_sg_levels_as_of_trade_date_not_filename]] 一族的資料契約精神）：
> 前者說「欄名進了歷史就不能改公式」，這裡說「**驗收指標必須與基線同一支掃描器**」。
> 兩者共同的根因都是：**測量口徑沒有 SSOT 時，時間序列上的比較是假的。**

另注意：`函式內 import 681` 是**縮排 import 近似**，會誤收 `try:` / `if TYPE_CHECKING:`
區塊內的頂層 import（高估）；`except-pass 87` 只抓 except 下一行就是 pass 的，
夾註解的抓不到（低估）。**近似口徑本身不是問題，沒寫下來才是。**

## 4. 結論與行動

### 4.1 派工表（本卡九項）

| 項 | J 判斷 | D 可偵測 | C 跨度 | 派 | 關鍵理由 |
|---|---|---|---|---|---|
| ① packaging | 中 | **低**（daemon 靜默跑舊碼） | 中 | **強模型定方案＋驗證**；sed 交便宜模型 | 執行機械但驗證不機械 |
| ② except-pass | **高** | **極低** | 低 | **最強模型，不可外包** | 唯一影響交易正確性 |
| ③ replay 搬家 | 中 | **高**（測試＋grep） | 中 | 便宜模型 | 護欄完整，讓它試錯 |
| ④ 拆巨型函式 | **高** | 中 | **極高**（1,019＋2,997 行同窗） | **強模型 ＋ 1M 窗** | C 軸不能用強度補 |
| ⑤ 函式內 import | 高 | 中 | 高 | 強模型 | 循環依賴＋config lazy 是架構決策 |
| ⑥⑦ paths/coerce | 低 | **高** | 低 | 便宜模型 | grep 驗收＝0 |
| ⑧⑨ 雜項 | 低 | 高 | 低 | 最便宜／手動 | 一行指令 |

**不建議對 ②④ 用加速模式**：那兩項瓶頸在判斷不在輸出，加速無益且更易漏。

### 4.2 順序修正

```
原卡：① → ③ → ② → ④ → ⑤ → ⑥⑦   （純依賴圖）
建議：①  ‖  ② → ③ → ④ → ⑤ → ⑥⑦  （② 提前並行，理由見 §2）
       ↑ 兩者改動區塊不重疊，可 worktree 隔離並行
```

### 4.3 開工前的口徑動作

在做任何子項之前，**先把 §6 的掃描腳本跑一次存成基線**，並把原卡「盤點基線」表與
「驗收」條款統一改標成同一支腳本的同一組參數（建議 `--include-cli`，因為 roma_cli 是
④ 的最大單體）。否則每個子項做完都要重新吵一次數字。
