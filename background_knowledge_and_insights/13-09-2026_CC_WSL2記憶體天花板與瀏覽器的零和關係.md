# WSL2 記憶體天花板與瀏覽器的零和關係

> **定位**：本篇是 2026-09-13 10:57–11:00 GMT+8 對**家用 PC 這一台機器**的資源配置稽核，起因是「現有硬體跑 Claude Code + 瀏覽器夠不夠」以及「手上 2 支閒置 16GB DDR4 要不要裝」。
> **性質聲明**：這是 **n=1 的單機單時點普查（census），不是實證研究**。全篇沒有對照組、沒有樣本期、沒有 CI，也不應該有——因為它量的是一個確定性的系統配置，不是一個帶雜訊的統計量。唯一具一般性的是第二節那條 WSL2 記憶體回收機制；其餘數字只對這台機器、這個時點有效。
> **最大限制**：量測當下瀏覽器只開了輕量分頁（3 個 browser family 合計 2.5GB），**這正是全篇最弱的一格**——真正的壓力情境（多分頁研報 + TradingView + 逐字稿）沒有被量到，見第六節待辦。

---

## 一、縮寫對照

- **CC** = Claude Code
- **WSL** = Windows Subsystem for Linux；**WSL2** 為其虛擬機架構版本
- **DIMM** = Dual In-line Memory Module，記憶體模組／插槽
- **IMC** = Integrated Memory Controller，CPU 內建記憶體控制器
- **XMP** = Extreme Memory Profile，記憶體廠商預設的超頻設定檔
- **JEDEC** = 記憶體標準組織訂定的保守預設時脈（未超頻狀態）
- **RSS** = Resident Set Size，行程實際佔用的實體記憶體
- **rank** = 記憶體模組的邏輯顆粒組；2Rx8 即雙 rank
- **vmmemWSL** = Windows 工作管理員中代表整個 WSL2 虛擬機的行程名
- **page cache** = 作業系統為加速檔案存取而保留的快取，可被回收

## 二、理論框架

### 2.1 WSL2 把單一實體記憶體池切成兩個互不相讓的池

原生 Linux 或原生 Windows 上，所有行程共用一個記憶體池與同一個回收器：瀏覽器要記憶體時，核心可以從別處回收給它。**WSL2 不是這樣**。它是 Hyper-V 上的真虛擬機，因此：

```
[ 實體 RAM ]
   ├── Windows 原生側（瀏覽器、Explorer、防毒…）
   └── vmmemWSL（整個 Linux VM，含其 page cache）
```

兩側**各自有獨立的記憶體管理器，彼此看不見對方的壓力**。Linux 核心不知道 Chrome 正在缺記憶體，Windows 也無法直接回收 VM 內部的頁面。這使得「總量還夠」與「實際順暢」脫鉤——這是本篇的核心機制。

### 2.2 預設值是零和分配，且偏向 VM

未提供 `.wslconfig` 時，WSL2 取 **host RAM 的 50%** 作為 VM 記憶體上限（舊版為 80% 或 8GB，依 WSL 版本而異）。這是一個**靜態的上限承諾**，不是動態協商。在 32GB 主機上等於預先把 16GB 劃給 Linux 側，不論 Windows 側當下是否更需要。

### 2.3 關鍵不對稱：氣球只會脹，不會消（除非明講）

VM 記憶體使用是**單調遞增**的：Linux 用掉的頁面（含 page cache）即使在行程結束後變成可回收狀態，**在 VM 內部仍算「已分配」，不會自動退還給 Windows**。因此 vmmemWSL 會一路漲到天花板就停在那裡。

`autoMemoryReclaim` 正是為此而生的開關（`gradual` / `dropcache` / `disabled`，預設等同不啟用）。**這是本篇唯一可外推到任何 WSL2 機器的結論**，其餘皆為本機配置。

### 2.4 兩種資源的瓶頸性質不同

- **CPU**：CC 絕大多數時間阻塞在 API round-trip，屬 network-bound。CPU 只在本地批次（ROMA 掃描／回測）時成為瓶頸，且為短暫尖峰。
- **記憶體**：是**容量敏感、非頻寬敏感**。這決定了第五節「時脈掉了也無所謂」的判斷。

## 三、量測設計

### 3.1 口徑

- **時點**：2026-09-13 10:57–11:00 GMT+8（開機後 12 分鐘，`up 12 min`）
- **雙側取數**：Linux 側 `lscpu` / `free -h` / `ps aux`；Windows 側經 `powershell.exe` 取 `Win32_PhysicalMemory`、`Win32_ComputerSystem`、`Win32_OperatingSystem`、`Win32_PhysicalMemoryArray`、`Win32_BaseBoard`、`Get-Process`
- **為何必須兩側都取**：第 2.1 節的機制決定了**單看任一側都會得到錯誤結論**。只看 `free` 會低估 WSL 的實際佔用（漏掉 page cache）；只看工作管理員則看不到 VM 內部誰在吃。

### 3.2 這裡沒有對照組，是刻意的

SAVEANA 慣例要求量化宣稱附同條件對照組與 CI。**本篇不提出任何量化宣稱**，因此不適用：所有數字都是確定性系統狀態的讀值（有幾支記憶體、上限設多少），重跑必得同值（除了隨負載變動的 used／free）。把 n=1 的配置讀值包裝成帶 CI 的「實證」會是假精確。

### 3.3 未執行的量測

沒有壓力測試、沒有跨時段取樣、沒有量到重負載下的實際爭用。**因此本篇無法回答「重載時會不會卡」，只能回答「配置上有多少餘裕」**。

| CPU | Intel i7-8700，6C/12T @3.2GHz（Coffee Lake） |
| 主機板 | ASUSTeK TUF Z390-PLUS GAMING (WI-FI) |
| DIMM 插槽 | **4 槽，已插 2**（ChannelA-DIMM1、ChannelB-DIMM1） |

## 五、結論與行動

### 5.1 結論

1. **當下餘裕充足**：18.7GB free，四個 CC session 只吃 1.4GB。**但這個結論的效力被 4.4 節的輕載瀏覽器限制住**——它證明的是「閒時很寬鬆」，不是「忙時不會卡」。
2. **真正的結構性風險不是總量不足，而是 2.1 的零和分割 + 2.3 的單向膨脹**。預設配置下 WSL 可無聲長到 15GB 並停在那，屆時 Windows 側只剩約 17GB 給瀏覽器與系統。
3. **CPU 無需處理**。
4. **加裝的理由不是「現在不夠」，而是閒置模組的機會成本為零，而 64GB 能讓 5.1-2 的張力整個消失**——WSL 給到 28GB 仍留 36GB 給 Windows，兩側都不必再權衡。

### 5.2 已執行

建立 `/mnt/c/Users/ongts/.wslconfig`（637 bytes，2026-09-13 11:00）：

```ini
[wsl2]
memory=12GB            # 32GB 主機用 12GB；升到 64GB 後改 28GB
processors=10          # 留 2 執行緒給 Windows，避免 ROMA 批次拖垮桌面
swap=8GB
autoMemoryReclaim=gradual   # 對治 2.3 的單向膨脹
```

**設計理由**：`memory=12GB` 比預設的 15GB **更低**是刻意的。WSL 側峰值需求**推估**約 8GB（4 session × 1.5GB + IBGW + monitor + docker；此為工程推估非實測，見「限制」節），12GB 已含餘裕；省下的 3GB 明確劃給瀏覽器。

⚠️ **尚未生效**，需 Windows 端 `wsl --shutdown`。該指令會**無預警終止整個 VM**：4 個 CC session、IB Gateway（PID 768 + Xvfb）、`monitor.py`、docker 全數中斷。已建議挑收工時點執行。

### 5.3 加裝 64GB 的執行注意

- **時脈可能下降**：現有為 2Rx8 雙 rank；插滿 4 支＝8 ranks，Z390 + i7-8700 的 IMC 常無法維持 XMP 2666，會退到 2400 或 2133。**依 2.4 節，此工作負載容量敏感而非頻寬敏感，故可接受**；不穩則關 XMP 走 JEDEC，或 DRAM 電壓調至 1.35V。
- **優先同型號**：新模組最好同為 `CT16G4DFD8266`，至少同為 2666 雙 rank。
- **免重排**：現有兩支已分居 A／B 雙通道，直接插空槽即可，開機後確認仍為 Dual Channel。

## 附錄

### 腳本

**本篇未產生腳本**，屬一次性互動查詢，故未落 `PY_DIR`（SAVEANA 慣例②僅在有跑腳本時適用）。若日後要做第六節的重載複測，應寫成腳本並落檔以便前後期對比。復現指令：

```bash
# Linux 側
lscpu | grep -E "Model name|^CPU\(s\)|Thread|Core|Socket"
free -h; swapon --show; uptime
ps aux --sort=-%mem | head -20
cat /etc/wsl.conf; cat /proc/version

# Windows 側（注意 /etc/wsl.conf 設了 appendWindowsPath=false，須用絕對路徑）
PS=/mnt/c/Windows/System32/WindowsPowerShell/v1.0/powershell.exe
$PS -NoProfile -Command "Get-CimInstance Win32_PhysicalMemory | Select BankLabel,DeviceLocator,Capacity,Speed,PartNumber | Format-Table"
$PS -NoProfile -Command "Get-CimInstance Win32_PhysicalMemoryArray | Select MemoryDevices,MaxCapacityEx"
$PS -NoProfile -Command "Get-CimInstance Win32_BaseBoard | Select Manufacturer,Product"
$PS -NoProfile -Command "Get-Process | Group-Object ProcessName | Select Name,@{n='MB';e={[math]::Round((\$_.Group|Measure-Object WorkingSet64 -Sum).Sum/1MB,0)}},Count | Sort MB -Desc | Select -First 15"
```

### ROMA 程式對照

本篇為本機作業環境稽核，**未引用或修改 ROMA runtime 程式**，故無 `file:line` 對照。

### 限制

- **n=1、單時點**，開機僅 12 分鐘，不含長時間運行後的碎片化與膨脹累積；
- **瀏覽器負載非代表值**（4.4 節已標），這是本篇最大缺口；
- `.wslconfig` **量測時尚未生效**，5.2 的效果為設計預期而非實測結果；
- 「4 session × 1.5GB」的峰值假設**未經實測**，係由 Node 預設 heap 上限與 1M context 推估，屬工程判斷；
- 未驗證新模組的實際相容性（尚未安裝），5.3 的時脈下降為 Coffee Lake 平台通則而非本機實測；
- 本機結論不可外推至公司 PC（不同硬體），僅 2.3 節機制具一般性。
